# Webhook 0.13.0 Operational Reliability Release Design

Date: 2026-06-23
Target package: `@nestarc/webhook`
Current version: `0.12.1`
Target version: `0.13.0`

## Summary

`@nestarc/webhook` already has the core outbound webhook engine expected from a production NestJS package: endpoint management, HMAC signing, retry, circuit breaker, delivery logs, per-attempt audit logs, endpoint snapshotting, multi-instance-safe polling, and worker observability.

The 0.13.0 release should not expand into a hosted webhook platform, generated customer portal, or generic workflow engine. It should make the existing self-hosted engine safer to operate in production by adding four focused capabilities:

1. Fix tenant ID storage compatibility for non-UUID tenant IDs.
2. Add producer-side idempotency so duplicate publish calls do not enqueue duplicate deliveries.
3. Add replay and retry operations v2 for operational recovery.
4. Add retention, minimization, and redaction controls for stored webhook data.

These changes preserve the package's current positioning: NestJS-native, PostgreSQL-backed, no separate infrastructure required.

## Research Basis

This design is based on:

- Local codebase review of `package.json`, `README.md`, `CHANGELOG.md`, `src/webhook.service.ts`, repository ports, Prisma adapters, SQL migrations, signer, delivery worker, and admin services.
- Existing package direction in 0.9.0 through 0.12.1: attempt logs, secret rotation, retry/degraded hooks, worker capacity controls, and backlog diagnostics.
- External ecosystem signals from Standard Webhooks, Svix, Hookdeck, Stripe, GitHub webhooks, AWS EventBridge/SNS, CloudEvents, and recent GitHub issues requesting retry, history, replay, signature verification, idempotency, and delivery audit trails.

## Goals

1. Keep 0.13.0 scoped to production reliability and compliance hardening.
2. Preserve current public APIs wherever possible and add optional parameters or optional port methods for new behavior.
3. Keep the default deployment model PostgreSQL-only.
4. Make duplicate publish attempts safe when callers provide an idempotency key.
5. Let operators recover failed deliveries in bulk and replay an event without writing SQL.
6. Give applications explicit controls for stored payload and response body retention.
7. Add tests that cover non-UUID tenant IDs, concurrent idempotent publish, replay, retry, and retention safety.

## Non-Goals

1. Do not build a customer portal UI in this release.
2. Do not generate REST controllers or auth policies for endpoint management.
3. Do not add Kafka, SQS, RabbitMQ, Redis, or BullMQ delivery backends.
4. Do not guarantee exactly-once receiver execution. The engine remains at-least-once; receiver idempotency is still required.
5. Do not add asymmetric signing, static egress IP, proxy support, or hosted delivery infrastructure.
6. Do not add a full event schema registry beyond the minimal fields needed by this release.

## Current State

### Implemented

- `WebhookService.send()`, `sendToTenant()`, and `sendToEndpoints()` save an event and enqueue deliveries in one repository transaction.
- `WebhookDeliveryWorker` claims pending deliveries, dispatches them, persists attempt logs, schedules retries, and recovers stale `SENDING` rows.
- `WebhookDeliveryAdminService` exposes `getDeliveryLogs()`, `getDeliveryAttempts()`, and single-delivery `retryDelivery()`.
- `WebhookSigner` supports Standard Webhooks-style `webhook-id`, `webhook-timestamp`, and `webhook-signature` headers, including multi-signature rotation overlap.
- SQL tables already use `tenant_id VARCHAR(255)` for endpoints and events.

### Gaps This Release Addresses

- The default Prisma event and endpoint repositories cast `tenant_id` to `uuid` on insert, even though the SQL schema and README examples treat tenant IDs as strings.
- There is no producer-side idempotency key, so duplicate publish calls can create duplicate events and delivery rows.
- Retry operations are single-delivery only. There is no bulk failed retry, event replay, or structured retry result.
- Stored event payloads and response bodies have no retention or purge policy.

## Release Scope

### 1. Tenant ID Compatibility Fix

### Problem

`webhook_endpoints.tenant_id` and `webhook_events.tenant_id` are `VARCHAR(255)`, but the Prisma adapters currently insert tenant IDs with `::uuid` casts. This breaks tenant IDs such as `tenant_123`, which the README shows as valid.

### Design

Keep tenant IDs as opaque strings throughout the package.

Required changes:

1. Remove `::uuid` casts from `tenant_id` writes in the default Prisma event and endpoint repositories.
2. Keep UUID casts only for table primary keys and foreign keys such as `id`, `event_id`, `endpoint_id`, and delivery IDs.
3. Keep existing `tenant_id::text = $1` reads working for backward compatibility, or simplify them to `tenant_id = $1` after tests prove equivalent behavior.
4. Add regression tests for `tenantId: 'tenant_123'` through endpoint creation, publish, delivery enrichment, delivery logs, and hooks.

### Migration

No SQL column migration is required for databases created from the package SQL because the column is already `VARCHAR(255)`.

Release notes must call out:

- UUID tenant IDs continue to work because they are also strings.
- Non-UUID tenant IDs now work with the default Prisma adapters.
- Applications that manually changed `tenant_id` to a database UUID type need to migrate back to `VARCHAR(255)` or provide custom repositories.

### Acceptance Criteria

- Creating an endpoint with `tenantId: 'tenant_123'` succeeds.
- Sending to `sendToTenant('tenant_123', event)` matches that endpoint.
- Delivery logs return `tenantId: 'tenant_123'`.
- Existing UUID-shaped tenant IDs continue to pass tests.

### 2. Producer-Side Idempotency

### Problem

Webhook producers often retry application operations after timeouts or transient errors. Without a producer idempotency key, repeated `send()` calls enqueue duplicate event rows and duplicate delivery rows.

### Public API

Add optional publish options:

```ts
export interface WebhookPublishOptions {
  /**
   * Application-provided key used to deduplicate publish attempts for the same
   * tenant and event type. The package stores this key but does not generate it.
   */
  idempotencyKey?: string;

  /**
   * Optional caller correlation ID for logs and future audit integrations.
   * This is not used for deduplication.
   */
  correlationId?: string;
}
```

Extend existing service methods without breaking existing calls:

```ts
send(event: WebhookEvent, options?: WebhookPublishOptions): Promise<string>;

sendToTenant(
  tenantId: string,
  event: WebhookEvent,
  options?: WebhookPublishOptions,
): Promise<string>;

sendToEndpoints(
  endpointIds: string[],
  event: WebhookEvent,
  tenantIdOrOptions?: string | WebhookPublishOptions,
  options?: WebhookPublishOptions,
): Promise<string>;
```

`sendToEndpoints(endpointIds, event, options)` should be accepted as a convenience overload. Existing `sendToEndpoints(endpointIds, event, tenantId)` calls remain valid.

### Repository API

Keep existing repository methods for non-idempotent publishing. Add an optional method for adapters that support idempotency:

```ts
export interface SavedWebhookEvent {
  id: string;
  created: boolean;
}

export interface WebhookEventRepository {
  // existing methods remain

  saveEventOnceInTransaction?(
    tx: WebhookTransaction,
    eventType: string,
    payload: Record<string, unknown>,
    tenantId: string | null,
    options: Required<Pick<WebhookPublishOptions, 'idempotencyKey'>> &
      Pick<WebhookPublishOptions, 'correlationId'>,
  ): Promise<SavedWebhookEvent>;
}
```

Behavior:

- If `idempotencyKey` is absent, use the existing save path.
- If `idempotencyKey` is present and the adapter does not implement `saveEventOnceInTransaction`, throw a clear error.
- If the event is newly created, enqueue deliveries as usual.
- If an existing event is returned, skip delivery creation and return the existing event ID.

### Database Changes

Add columns:

```sql
ALTER TABLE webhook_events
  ADD COLUMN idempotency_key VARCHAR(255),
  ADD COLUMN correlation_id VARCHAR(255);
```

Add a unique index scoped by tenant, event type, and idempotency key:

```sql
CREATE UNIQUE INDEX IF NOT EXISTS webhook_events_idempotency_key_idx
ON webhook_events (
  COALESCE(tenant_id, ''),
  event_type,
  idempotency_key
)
WHERE idempotency_key IS NOT NULL;
```

The `event_type` scope allows one business operation to publish different event types with the same caller key when needed. Callers that want cross-event uniqueness should prefix keys consistently.

### Concurrency

The Prisma adapter should use `INSERT ... ON CONFLICT ... DO NOTHING` followed by a `SELECT` inside the same transaction, or an equivalent CTE, so concurrent duplicate publish attempts return the same event ID.

### Acceptance Criteria

- Two sequential sends with the same tenant, event type, and idempotency key return the same event ID.
- Concurrent duplicate sends create exactly one event row.
- Duplicate sends create only one set of delivery rows.
- Same idempotency key with a different event type creates a separate event.
- Same idempotency key under a different tenant creates a separate event.
- Without `idempotencyKey`, behavior remains unchanged.

### 3. Replay and Retry Operations v2

### Problem

Current admin recovery is limited to one failed delivery at a time. Operators need bulk recovery and event replay for customer support and incident response.

### Public API

Extend `WebhookDeliveryAdminService`:

```ts
export interface RetryDeliveryOptions {
  reason?: string;
}

export interface RetryFailedDeliveriesFilters extends DeliveryLogFilters {
  endpointId?: string;
}

export interface RetryFailedDeliveriesResult {
  matched: number;
  retried: number;
  skipped: number;
}

export interface ReplayEventOptions {
  endpointIds?: string[];
  tenantId?: string;
  reason?: string;
}

export interface ReplayEventResult {
  eventId: string;
  deliveriesCreated: number;
  endpointIds: string[];
}

class WebhookDeliveryAdminService {
  retryDelivery(
    deliveryId: string,
    options?: RetryDeliveryOptions,
  ): Promise<boolean>;

  retryFailedDeliveries(
    filters: RetryFailedDeliveriesFilters,
    options?: RetryDeliveryOptions,
  ): Promise<RetryFailedDeliveriesResult>;

  replayEvent(
    eventId: string,
    options?: ReplayEventOptions,
  ): Promise<ReplayEventResult>;
}
```

### Retry Semantics

- `retryDelivery()` remains backward-compatible and still returns `boolean`.
- Manual retry should only update `FAILED` rows.
- Manual retry should set `status = 'PENDING'` and `next_attempt_at = NOW()`.
- Manual retry should ensure at least one additional attempt is possible by setting `max_attempts = GREATEST(max_attempts, attempts + 1)`.
- Retry operations must not change the original event payload, endpoint snapshot, response body, or attempt history.

### Bulk Retry Semantics

`retryFailedDeliveries()` should:

- Match only `FAILED` deliveries.
- Support filtering by endpoint, event type, status-compatible delivery filters, and time range.
- Default `limit` to `100` and reject values above `1000` unless a future explicit unsafe override is added.
- Return counts for matched, retried, and skipped rows.

### Event Replay Semantics

`replayEvent()` should:

- Reuse the original `webhook_events.id` so receiver-side idempotency can detect the replay.
- Create new delivery rows for selected currently active endpoints.
- Ignore inactive endpoints in 0.13.0. Replaying to inactive endpoints is deferred.
- Use current endpoint URL and signing secret snapshots at replay time.
- Reject replay if the event payload has been purged by retention.
- Return the endpoint IDs that received replay deliveries.

This is intentionally not a "clone event" feature. A clone that creates a new event ID should be considered separately after 0.13.0.

### Repository API

Add optional delivery repository methods:

```ts
retryFailedDeliveries?(
  filters: RetryFailedDeliveriesFilters,
  options?: RetryDeliveryOptions,
): Promise<RetryFailedDeliveriesResult>;

replayEvent?(
  eventId: string,
  options?: ReplayEventOptions,
): Promise<ReplayEventResult>;
```

If a custom repository does not implement these methods, the admin service should throw a clear unsupported-operation error.

### Acceptance Criteria

- Retrying a failed delivery grants one immediate manual attempt.
- Bulk retry updates only failed rows matching the filter and limit.
- Event replay creates new delivery rows without creating a new event row.
- Replay uses current endpoint snapshots, not the original delivery snapshot.
- Replay fails with a clear error after event payload purge.
- Public contract tests cover the new service methods and result types.

### 4. Retention, Minimization, and Redaction

### Problem

The package stores event payloads, delivery response bodies, attempt response bodies, and errors. This is useful for support, but it can create avoidable privacy and compliance risk when payloads or receiver responses include sensitive data.

This section is not legal advice. Defaults and documentation for retention behavior are marked 법무 검토 필요. Any implementation that processes sensitive payloads or response bodies is marked 보안 검토 필요.

### Public Options

Add optional module configuration:

```ts
export interface WebhookRetentionOptions {
  /**
   * Disabled by default. When set, event payloads are replaced with an empty
   * object after all deliveries for the event are terminal and the event is
   * older than this many days.
   */
  eventPayloadRetentionDays?: number;

  /**
   * Disabled by default. When set, terminal delivery response bodies are set to
   * null after the delivery is older than this many days.
   */
  deliveryResponseBodyRetentionDays?: number;

  /**
   * Disabled by default. When set, attempt response bodies are set to null after
   * the attempt is older than this many days.
   */
  attemptResponseBodyRetentionDays?: number;
}

export interface WebhookRedactionOptions {
  /**
   * Applied before payload persistence and delivery dispatch. This is a
   * minimization hook, not a storage-only redaction hook.
   */
  sanitizePayload?: (
    payload: Record<string, unknown>,
    context: { eventType: string; tenantId: string | null },
  ) => Record<string, unknown>;

  /**
   * Applied before response bodies are stored on delivery rows and attempt rows.
   * Return null to suppress response body storage.
   */
  sanitizeResponseBody?: (
    body: string,
    context: { endpointId: string; eventId: string; statusCode: number | null },
  ) => string | null;
}

export interface WebhookModuleOptions<TPrisma = unknown> {
  // existing options
  retention?: WebhookRetentionOptions;
  redaction?: WebhookRedactionOptions;
}
```

### Important Semantics

- `sanitizePayload` changes both the stored payload and delivered payload. This must be documented clearly.
- The package should not promise storage-only event payload redaction in 0.13.0 because the worker currently dispatches from `webhook_events.payload`.
- Payload purge must only affect events whose deliveries are all terminal.
- Purged payload should be represented as `{}` because `webhook_events.payload` is currently `NOT NULL`.
- `replayEvent()` must reject a purged event payload.

### Database Changes

Add payload purge metadata:

```sql
ALTER TABLE webhook_events
  ADD COLUMN payload_purged_at TIMESTAMPTZ;
```

Response body columns are already nullable and need no schema change.

### Repository API

Add an optional method:

```ts
export interface WebhookRetentionPurgeResult {
  eventsPurged: number;
  deliveriesPurged: number;
  attemptsPurged: number;
}

export interface WebhookDeliveryRepository {
  purgeExpiredData?(
    options: Required<WebhookRetentionOptions>,
    now?: Date,
  ): Promise<WebhookRetentionPurgeResult>;
}
```

The repository can live on the delivery repository because purge decisions need delivery terminal-state checks and delivery/attempt response body updates.

### Scheduling

Do not add a new automatic interval by default. Expose an admin/service method first:

```ts
class WebhookRetentionAdminService {
  purgeExpiredData(now?: Date): Promise<WebhookRetentionPurgeResult>;
}
```

Applications can call this from their own scheduler. A package-managed purge interval can be added later if demand is clear.

The service should be registered by the module when default repositories are used. If retention options are absent, `purgeExpiredData()` should return zero counts instead of throwing.

### Acceptance Criteria

- Response body sanitizer applies to delivery rows and attempt rows.
- Payload sanitizer applies before event persistence.
- Purge does not remove payloads for events with `PENDING` or `SENDING` deliveries.
- Purged events set `payload = '{}'::jsonb` and `payload_purged_at = NOW()`.
- Replay of a purged event fails with a clear error.
- Retention options default to disabled.
- README documents that payload minimization affects delivered content.

## Risks

1. Idempotency unique index design can surprise users if they reuse keys across event types. This design scopes uniqueness by tenant, event type, and key to reduce that risk.
2. Custom repository users will not get idempotency, replay, or retention automatically. The package must fail clearly when an optional method is required but missing.
3. Manual replay can produce duplicate side effects in receivers that do not implement idempotency. Documentation must state this plainly.
4. Retention and redaction defaults may have legal and compliance implications. 법무 검토 필요.
5. Response body redaction may hide useful debugging data. Applications should choose policy per product risk.
6. Payload minimization changes delivered payloads, not just stored payloads. Documentation must avoid implying otherwise. 보안 검토 필요.

## Decisions Locked For This Spec

1. `correlationId` is stored on `webhook_events` in 0.13.0. Surfacing it in delivery logs is deferred.
2. Bulk retry defaults to `limit: 100` and rejects limits above `1000`.
3. `replayEvent()` targets currently active endpoints only.
4. `WebhookRetentionAdminService` is exported by the module and returns zero counts when retention is not configured.
5. `verifyWithTolerance()` is a Should item, not a release blocker.

## Final Recommendation

Ship 0.13.0 as an operational reliability release:

- `Fixed`: tenant ID compatibility in default Prisma adapters.
- `Added`: idempotent publish, bulk retry, event replay, retention purge, payload/response sanitizers.
- `Changed`: manual retry grants at least one additional immediate attempt while keeping the existing boolean return contract.
- `Security`: optional timestamp-tolerant signature verification helper if it fits the release budget. 보안 검토 필요.

The release should be marketed as:

> Production hardening for self-hosted NestJS webhooks: safe tenant IDs, idempotent publishing, operational replay, and explicit data retention controls.
